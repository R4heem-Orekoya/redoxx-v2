## Building in Public

For the past year, I've been building almost entirely in public. Every feature, every bug, every late-night refactor — all out in the open. Here's what I've learned.

It forces better decisions. When you know someone might read the commit message or watch the PR, you write better code. You write clearer commit messages. You actually write that test you've been putting off.

## The Upside

Building in public attracts the right kind of attention. Other engineers point out blind spots. Users show up before you've even launched.

```ts
const feedback = await getFeedback();
```

## The Downside

It's exhausting. You feel the weight of the audience even when nobody's watching. Every half-baked commit feels like a failure.

> Build as if everyone is watching, but write code as if no one is.

That's the balance. Ship the work, share the journey, but don't let the performance paralyse you.

## Practical Tips

1. Write the post before you build the feature — it clarifies the scope.
2. Share the ugly parts, not just the wins.
3. Engage with every comment, even the critical ones.

The network you build by building in public is the best moat you'll ever have.
